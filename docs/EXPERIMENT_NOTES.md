## 2. EMA 係数による「滑らかさ vs 反応速度」

`smoothed = prev * α + current * (1 - α)` (`BandAnalyzer.Configuration.smoothing`)

| α | 体感 | 用途の当たり |
| --- | --- | --- |
| 0.3 | | |
| 0.5 | | |
| 0.7 (既定) | | |

- 時定数の目安: hop が約 12ms (2048/4 @44.1kHz) のとき、
  α=0.7 で ≒ 33ms、α=0.9 で ≒ 110ms で目標値の 63% に到達する。
- ビート検出 (`BandAnalyzer.BeatDetection`) は平滑化 **前** の値を使っている。

## 3. スピーカー再生 vs イヤホン再生でのマイク検出感度差

- スピーカー再生: 直接音を拾えるので想定どおり動く。音量と端末の距離で大きく変わる。
- イヤホン/ヘッドフォン出力: **原理的にマイクへ音が届かない**。
  アプリ側では `AudioSessionObserver.isUsingHeadphoneOutput` で検出し、画面に注意表示を出している。
- 有線/Bluetooth ヘッドセットの **マイク** に入力が切り替わると感度と帯域が落ちる。
  `.allowBluetooth` (HFP) を有効にすると 8/16kHz の狭帯域に落ちて高域が消えるため、
  `MicInputSource` では `.allowBluetoothA2DP` のみ許可している。

## 4. 静音環境と生活音がある環境での挙動差

- 静音環境: floor を下げる (-80dB 付近) と細かい変化まで拾える。
- 生活音あり: floor を上げないと常時 mid が張り付き、色が飽和して動かなくなる。
- `AVAudioSession.Mode` を `.measurement` にして OS 側の AGC / EQ を切っている。
  `.default` に戻すと AGC が効いて小音量でも派手に動くが、音量変化の情報が失われる。

## 5. PlayerTapInputSource へ切り替えたときに、この設計がどこまで無改修で通用するか

想定される差分:

| 層 | 想定される改修 |
| --- | --- |
| `AudioInputSource` | なし (プロトコルは同一) |
| `VisualizerEngine` | 生成する具象型の切り替えのみ。`bufferPublisher` の購読以降は同一 |
| `AudioAnalyzer` 以降 | なし (`AVAudioPCMBuffer` しか見ていない) |
| `AVAudioSession` | `.playAndRecord` → `.playback`。マイク権限のフローが丸ごと不要になる |
| チューニング値 | 要調整。マイク経路のノイズフロアが無くなるため floor を下げられる |

- 検証手順: 音源ファイルをターゲットに追加し、`VisualizerEngine` の `source` を
  `PlayerTapInputSource(fileURL:)` に差し替えて、解析層以降が無改修で動くか確認する。
- ここで洗い出した差分が、将来のリアルタイム信号処理パイプライン (Nyx 感覚同期など) で
  「入力の抽象化をどこに引くべきか」の判断材料になる。

## 参考: 実装上のメモ

- `vDSP_fft_zrip` の出力は真の DFT 係数の 2 倍で、Nyquist 成分が `imagp[0]` に詰め込まれている。
  `FFTProcessor` では `imagp[0] = 0` にしてから magnitude を取り、
  `2 / fftSize` (Hann のコヒーレントゲイン 0.5 込み) で正規化している。
  結果として「振幅 A の正弦波 → 該当ビンの magnitude ≒ A」になり、単体テストで検証している。
- Hann 窓のため、ピークの隣接ビンには約 1/2 の値が漏れる。これは正常。
- 帯域の平均 magnitude はビン数で割るため、帯域幅の広い high は構造的に値が小さくなる。
  `BandAnalyzer.BandGain` (既定 low 0dB / mid +4dB / high +10dB) で補正している。
  実機で「高域が反応しない」と感じたら最初に触る値。
